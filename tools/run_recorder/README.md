# Run recorder

Test equipment for the ABB production readiness plan (TGuideWeldingHMI
`docs/abb_production_readiness_plan_v1.md`, sections 5.2, 5.3 and 6.3). Nothing here is deployed
to a controller and nothing in the production code imports it.

The recorder watches one TG run on an ABB controller over RWS and writes down what the
**controller** did: when each weld span ran, how far and how fast the TCP went, how long the
welder's weld-on output was high, and the weld data in effect. `checks.py` then compares that with
what the HMI served. The HMI's own report is not consulted: on ABB it reports every run as
completed (readiness plan Q3, deferred).

**The recorder is read-only.** `rws_reader.RwsReader` only issues GET requests through one cookie
session (TG_RoboCal `lessons_learned.md` L9), so it cannot write data, move the program pointer,
take mastership or change a signal. `bench_cycle.py`, `hmi_case.py` and `campaign/` are the
exception, and they are not part of the recorder: they start parts over RWS (and the stand-in HMI
uploads a module), for a virtual controller only.

| `campaign/` | The VC campaign: `make_fixtures.py` (fixtures from copies of real projects, regenerated by the Weld Planner headless with `planner_generate.py`), `run_campaign.ps1` (every fixture through `hmi_case.ps1`), `station_variant.py` (station 1 expectations), `summary.py` (results table), `vc_modules/` (VC-only helper programs: `TGIndexStn1/2` present a station with Production Manager's own index hook, `TGHomeStn` homes the positioner between cases, `TGTimeMove` times a move with the controller's clock). `present_station.py` presents a station directly over RWS when none is in position (TG_Main then refuses every part with 80001, so the TGIndexStn helpers, which run as a part, cannot). ## Use

On the VC, with a stand-in HMI (no C++ HMI needed):

```
python bench_case.py --label F1 --mod <exported .mod> --params params.json --expect expect.json
```

`params.json` is the list of weld parameter sets served to welds 1..N (field names as in
`hmi_prototype/abb_server.py`, e.g. `travel_speed` in IPM). `expect.json` is
`{"welds": [{"seam_length_mm": 20.0}, ...]}` from the planner. The seam length must come from the
planner, not from the module under test: the E59 module has a 0 mm span, and only the planner's
seam length shows how much weld is missing.

With the real HMI in the loop on the VC (the HMI build's own ProgramData is used):

```
.\hmi_case.ps1 -Fixture F3.tgs -Expect F3_expect.json -Label F3 -OutDir results
.\campaign\run_campaign.ps1 -Dir C:\abb_readiness\vc_campaign
```

On a real cell (socket start, Production Manager), start
`python recorder.py --out run.json` first; it stops when the program pointer returns to the
profile's idle module (`gapMain`) after the weld module ran. Then
`python checks.py run.json --sent sent.json --expect expect.json`.

## What is sampled

Measured on VC A (RobotStudio MonarchRS, system 4600-803651, RW 6.15.8029), 2026-10-28:

- Every tick: program pointer, TCP in `wobj0`, `wdTG_Weld`, the weld-on output and the
  arc-detect input; once the weld module is loaded, the TCP in each work object its arc spans
  use, and for a coordinated work object the joints of the positioner it moves with. About
  13-20 ticks per second on one session.
- In turn, one per tick: execution state, the profile's other welder outputs, `sdTG_Weld`, the
  TG_Comms weld flags, and each arc-span work object (its `oframe` is the frame the HMI served).
- When the weld module appears: its file from `$home/TGS/<stTG_ProgName>.mod`, its weave and one
  other LOCAL datum read while it is loaded.
- After the run: the event-log entries written during it.

## The checks (plan section 6.3)

| Id | Check |
|---|---|
| A1 | The arc span covers some distance (0 mm is the E59 shape). TCP travel >= 0.9 x seam length / weld_speed. Steady seam speed within 5 % of weld_speed (10 % when weaving). Weld-on output high >= 0.9 x the same time. Coordinated: the positioner at the module's planned axis values at the seam start and end (+-0.5 deg). |
| A2 | Weld data in effect = what was served (stand-in HMI) or what the project says the HMI must send (real HMI), as `TG_Weld.sys` builds it (IPM x 0.4233333; Fronius path clamps arc length to -10..10, Miller passes it). Constant during the weld. Welder outputs follow it. Weave reads back as declared and as set on the weld. |
| A3 | No error or warning in the event log during the run. |
| A4 | Every weld span reached. A span the program pointer never reached was skipped or aborted on the robot, which the HMI does not report. |
| A5 | No hang: the program pointer leaves each weld span within 2 x its weld time + 10 s, and the run ends on its own. |
| A6 | The work object's `oframe` during the weld = the expected frame (+-0.1 mm): the module's seed for a coordinated weld; for a base weld the nominal at the weld's positioner index, moved by the weld's stored touch-up (from the fixture). |
| Refused | A fixture with `{"outcome": "refused"}`: no weld module ran, the robot logged the refusal, nothing else went wrong. |
| Aborted before the arc | A fixture with `{"outcome": "aborted_before_arc"}` (the chain-entry guard): the weld module ran, no arc span was reached, the part ended. The event log is listed, not judged: the guard writes to the pendant only (R5). |

RWS facts found on the way:

- RWS on RW 6.15 never fills the **motion** pointer (`pcp` returns it with only an error link). The
  recorder follows the **program** pointer, which stays on a `fine` `ArcLEnd` until the robot
  arrives.
- The TCP is read about every 0.05 s, and a fast weld moves 0.6 mm per tick, so the TCP is rarely
  seen exactly at a target. Travel time is the steady speed along the planned path (least squares
  over the samples inside the seam) extrapolated to the two ends.
- Reading a robtarget in the work object of a **deactivated** mechanical unit makes the controller
  log 50066 "Robot not active" (an error entry in the run being judged). Reading the unit's
  joints logs nothing, so the recorder reads a coordinated work object's TCP only in ticks where
  its unit reads active.
- The positioner package loads `StnIndCfg12` on the fly; the weld module is recognised by its
  routine name (`stTG_ProgName`), not by being new.

## Limits

- The VC runs on the PC's CPU, and the clocks here are the PC's. With another job loading the PC,
  a 100 mm move the controller timed at 1.06 s took 2.4 s by the PC's clock
  (`campaign/vc_modules/TGTimeMove.mod`). A seam-speed miss recorded while RWS reads were slow
  (median above 0.085 s) says so, and is re-run on an idle PC before it counts.
- The HMI runs in Simulation mode, so localization returns no correction unless the case plants
  one: `hmi_case.ps1 -PlantedOffset x,y,z,rz,ry,rx` sets the HMI's `HMI_SIMULATION_PART_OFFSET`
  for that case (the camera test mode), and A6 then expects every served frame moved with the
  part. A coordinated weld's expectation needs the part's pose in the station frame, which
  `hmi_case.py --fixture` reads from the project.
- Station 1 is presented by `campaign/vc_modules/TGIndexStn1.mod` calling Production Manager's own
  index hook, not by PM dispatching a part (that needs the part-run input, which RWS cannot set in
  AUTO).

- Welder signal names are per cell (`profiles/`). Only VC A's Miller profile exists. Cell 2's
  Fronius outputs need their own profile, written from that cell's EIO.
- Arc-detect on a VC is simulated, so it shows that the program asked for an arc, not that one
  struck. The real cell's checklist (plan section 6.6) covers the strike.
- The recorder cannot read `TPWrite` text. A weld the robot skips on purpose (chain-entry guard)
  shows as "never reached", without the reason (plan item R5).
