Monarc Cell Teardown

An ABB FlexArc-style arc-welding cell: one IRB 4600 serving a two-station indexing positioner, a Miller welder on EtherNet/IP, and a PLC on PROFINET. The interesting engineering is not in the motion — it is in how the programmer measures each part's rotation with the welding wire and re-indexes the whole program around it.

Orientation

The cell

A single IRB 4600 stands beside an IRBP D600 L2000 D1200 Type A — a double-ended indexing positioner. It presents two independent work stations to the robot, one at a time, and swaps them through a 180° index. While the robot welds one side, the operator loads the other behind a rotating shield wall. Troax fencing, one operator stand, a SafeLock VAR PLe gate, an AB-855D stack light.

The positioner appears in RobotWare as three mechanical units, not one:

MOC.cfg — mechanical units
Mech unitJointsActivation relayFeedbackRole
STN1ARM1, PLATE1soACT_STN1siSTN1_ACTStation 1 tilt + turntable
STN2ARM2, PLATE2soACT_STN2siSTN2_ACTStation 2 tilt + turntable
INTERCHINTERCH, INTERCH_PLATE1, INTERCH_PLATE2soACT_INTCHsiINTCH_ACTThe 180° index axis plus both turntables, so all three move as one during the swap

Both STN1 and STN2 carry -allow_move_of_user_frame, so work objects can be coordinated to them. The turntables (PLATE1, PLATE2) are declared -independent_joint_on with a joint bound of ±20 rad against a maximum of ±1.25×106 rad — the hardware can spin continuously, though no RAPID in this backup uses IndAMove.

The application layer is ABB's Production Manager (internally "GAP"). main() is a single line — ExecEngine; — and everything after that is the engine dispatching parts. A part is a partdata record naming a routine, a station number and an ID; the PLC or the FlexPendant Production Screen picks one, the engine runs it.

Where the code lives

The framework modules (Irbp1Prc, Irbp1EEv, GoSafeUsr, BE_Mnu) come from the option media and are auto-loaded via SYS.cfg → CAB_TASK_MODULES. The cell-specific work is in Utility.sys, TorchServices.sys, mDeclarations.sys, wobj_Database.sys, m2ndLoadPos.sys and the mRS4xxxxx.mod part programs. Four modules are encrypted and unreadable: GAP_USER.sys, GAP_PARTADV.sys, GAP_PARTADV_SHRD.sys, ProdScr.sys.

Sequence

One part, end to end

Every production routine — RS461117_Stn1, RS462509_Stn2, and by inference the ~20 that live only in the station file — follows the same eleven-step skeleton. It is worth learning once, because it is copy-pasted verbatim.

! 1  clear the handshake outputs
SetDO doOK_Unclamp, 0;   SetDO doAllWeldsComplete, 0;
SetDO doWld1TouchOn, 0;  SetDO do5_WireBrake, 0;
DeactUnit STN1;
MoveAbsJ jposSafe\NoEOffs, v1000, z50, tWeldGun;

! 2  extend wire 0.3 s so the cut lands on solid wire
SetDO soAwManFeedFwd, 1;  WaitTime 0.3;  SetDO soAwManFeedFwd, 0;

! 3  trim to a known stickout, then lock the wire
MoveJ ..., v1000, z100, tWeldGun;
WireCutter;
SetDO do5_WireBrake, 1;
MoveJ pWireIntermediate, v200, z50, tWeldGun;

! 4  ask the PLC to drive the clamp to the programmed start position
SetDO doOK_Unclamp, 1;
WaitTime 1;
WaitDI diReadyToResumeProg, 1;
SetDO doOK_Unclamp, 0;

! 5  declare the nominal table angle, then take the drives
initialHeadstockRot := -22;
ActUnit STN1;

! 6-8  wire touch search, correction maths, welds  (see "Finding the part")

! 9  tell the PLC it may unload
SetDO doAllWeldsComplete, 1;
DeactUnit STN1;
MoveAbsJ jposSafe\NoEOffs, v200, z50, tWeldGun;

Condensed from mRS462509.mod:187. Steps 2–3 exist purely so the welding wire becomes a repeatable mechanical probe in step 6.

Two things about this skeleton matter more than they look:

  • The clamp is the PLC's, not the robot's. The robot never actuates the fixture. It raises doOK_Unclamp, the PLC moves the clamp and answers diReadyToResumeProg. The same handshake appears in clampBrakeTest, so it is also the manual test path. Clamp position feedback (diStn1ClampOpen/Closed/AtPos1/AtPos2) is mapped but never read in RAPID — the PLC owns that logic.
  • Every routine opens with DeactUnit and closes with DeactUnit. That is not defensive style, it is mandatory — see the next two sections.

There is also a ..._NoIO twin of most part routines (RS461117_Stn2NoIO, RS462509_Stn2NoIO) which drops the clamp handshake, the wire trim and the search, and just welds the nominal path. These are the dry-run / air-cut versions used at the pendant.

Trap in the NoIO twins

The _NoIO routines do not set initialHeadstockRot and do not search, but the twist-compensation maths in the full routines reads that same shared PERS num. Running a _NoIO routine leaves whatever value the last full part wrote. It is harmless in the _NoIO path itself, but it means the variable's value at any moment tells you nothing about which part it belongs to.

Interchange

Swapping the two sides

The index is not written by the customer — it is IndexToStn1 / IndexToStn2 in Irbp1Prc, from the Positioner functional package. Reading it is the fastest way to understand the cell's rhythm:

  1. If bInterchCalib1 is false, run CalibIntch1 (CalibInterch1Proc). The calibrated index positions are nInterchStn1 = -0.249999° and nInterchStn2 = 179.901° — note the 0.1° asymmetry, that is real calibration data, not a typo.
  2. ActInterch1 activates the 3-joint INTERCH unit and calls GetNextPartAdv for both stations, then MechUnitLoad INTERCH, 2 and MechUnitLoad INTERCH, 3 with each side's payload. If a part's partadv.load.mass ≤ 0.001 it silently substitutes the 200 kg default and writes an event-log warning.
  3. A single MoveAbsJ at sdInterch1 = [1000,500,5000,180] drives the index axis and both turntables at once: station 1 to the incoming part's process angle, station 2 to the outgoing part's load angle. The two sides are pre-oriented during the swing — no separate positioning move afterwards.
  4. WaitTime nTorqueTime (0.4 s) to let the torque settle, then DeactInterch1 and WaitUntil IsMechUnitActive(INTERCH)=FALSE.
partadv is the part's positioner recipe

Each part carries a partadv record holding three angles — load, process, service — plus its loaddata. ActStn1 pulls it with GetNextPartAdv and applies the payload with MechUnitLoad STN1, 2. So payload and table angles are data per part, not code. Editing them from the pendant's Production Manager → Part view changes the motion without touching RAPID.

The collision guard for the swing is an execution-engine event, not inline code. Utility.sys registers:

CONST ee_event ee_ArmsAtZero := [EE_CLOSE_JIG,"ArmsToZero_DPos","",1,GAP_STN_1+GAP_STN_2];

so before the jig closes on either station, ArmsToZero_DPos levels both tilt axes to eax_b = 0. That is what keeps a tilted fixture from clipping the shield wall on the way round.

ArmsToZero_DPos ends with Stop;

Utility.sys:278 — the routine bound to EE_CLOSE_JIG finishes with a bare Stop;. In a production cycle that halts the program and requires an operator start. It reads like leftover commissioning debug that never got removed. Verify against the running plant before deleting: if production has been running, either the event is not firing or the operators have been living with the stop.

A second load position, driven from the HMI

m2ndLoadPos.sys lets the operator ask for an arbitrary table angle at load time. The PLC writes the angle to the group input giTableAngle, the sign to diTableAngNeg, then pulses siSTN1LoadPos2. An ISignalDI interrupt fires a TRAP which activates the station, moves the table to that angle, then arms a temporary joint world zone (WZHomeJointDef, tolerance 2° tilt / 3° rotate) that drives soAtSTN1_2ndPos back to the PLC.

Motion inside a TRAP

The TRAP does ActUnit → MoveJ → DeactUnit. It can fire at any point in the cycle, from a PLC signal, and it moves the positioner while holding the robot at CRobT(). If the torch is inside the part when the request lands, the table rotates around it. Whatever interlock prevents that lives on the PLC side and is not visible from the robot.

Electrical constraint

Shared drives, one station at a time

Count the hardware. MOC.cfg declares five positioner measurement nodes (pos1_1…pos1_5 on measurement link 2) — ARM1, PLATE1, ARM2, PLATE2 and the index axis. The option list declares three drive units: ADU-790A in position X3, Y3, Z3.

Five motors, three drives. The gap is closed with contactors, and RobotWare's activation relays are cross-connected straight onto them:

K3, K4 and K5 are mutually exclusive by construction — they connect three different motors to the same drive. Which gives the cell's hardest rule:

STN1 and STN2 can never be active together

This is why every routine is bracketed in ActUnit/DeactUnit, why mDeclarations carries the odd little initialize() / initialize2() pair (an ActUnit immediately followed by DeactUnit, to force a known state), and why the drive I/O board is configured -StateWhenStartup "Deactivated".

Testing.mod:152 positionTest does ActUnit STN2 … ActUnit STN1 with no intervening DeactUnit. Expect an activation failure at the second ActUnit.

The same sharing shows up in the RAPID data, and this is the subtler trap. PartR1S1.ProgStn1 and PartR1S2.ProgStn2 both write jtCurrent.extax.eax_b and eax_c. The two stations reuse the same external-axis slots, because they reuse the same drive-module axis numbers.

extax values are only meaningful with the matching station active

eax_b is the tilt/arm (±20° in the test moves; ArmsToZero_DPos zeroes only this one), eax_c is the turntable. Under INTERCH the slots shift again — eax_b and eax_c become the two stations' angles and eax_d becomes the index axis. A robtarget copied from a station-1 routine into a station-2 routine will command station 2's axes to station 1's angles without complaint.

One more detail with operational bite: the shared drive I/O board carries -TrustLevel "DRVIO_TRUSTLEVEL", defined as ActionWhenLost "NONE", ReportWhenLost "NONE". If that board drops off the bus, nothing stops and nothing is logged.

The core technique

Finding the part

These are long tubular weldments clamped in a headstock. They do not land at the same rotation twice. The programmer's answer is to measure the part with the welding wire and then move the part to meet the taught program — rather than recompute the program to meet the part.

Step 1 — the wire is the probe

SmarTac is configured as smtMiller1: touch sensing through the welder, not through a separate sensor card.

PROC.cfg — SMARTAC_SIGNALS, active profile
FunctionSignalNote
Sensor ondoWld1TouchOnEnergises the wire for touch sensing
Sensor activediWld1TouchActiveWelder confirms sensing is live — RAPID waits on this
DetectdiWld1TouchedContact; the signal handed to SearchL/SearchC

Hence the wire choreography at the top of every part: feed 0.3 s, cut at the trim station, then do5_WireBrake to stop the spool creeping. A search is only as repeatable as the stickout.

A second profile, smtLaser (di3_SMTAC_LaserDet in, Local_IO_0_DO10 out), is fully configured but not selected — SMARTAC_SETTINGS points at smtMiller1. Its footprint is all over the code as commented-out laser searches, three Laser1/Laser2/Laser2p2 tooldata, and a working Testing.laserTest. A laser trial that was tried and shelved.

Step 2 — two different corrections, depending on the part

mRS461117 — Cartesian offset

A circular search gives X and Z, a linear search gives Y, and the delta is applied by wrapping every single target in Offs():

SearchC\Stop, diWld1Touched, pSearchPt_1W, pSearch_1W_8, pSearch_1W_12, v5, tWeldGun\WObj:=wobj_Stn1;
dTrans.x := pSearchPt_1W.trans.x - pSearch_1W_8.trans.x;
dTrans.z := pSearchPt_1W.trans.z - pSearch_1W_8.trans.z;
SearchL\Stop, diWld1Touched, SearchPt_1L, SearchTo_1L, v5, tWeldGun\WObj:=wobj_Stn1;
dTrans.y := SearchPt_1L.trans.y - SearchPt_1LIdeal.trans.y;

ArcLStart Offs(p461117_1_140, dTrans.x, dTrans.y, dTrans.z), v300, sm3_16_ft_block, wd3_16_ft_block_095, fine, ...

mRS462509 — rotational re-index, and this is the clever one

The circular search does not read a position. It reads the positioner's own angle at the moment of contact:

SearchC\Stop, diWld1Touched, pSearchPt_1W, pSearch_1W_n22, pSearch_1W_n18, v5, tWeldGun\WObj:=wobj_Stn1;
angularDisp1 := pSearchPt_1W.extax.eax_c;          ! where the feature actually is
TPWrite "  Angular  Reading  Station  1 (462509) " + ValToStr(angularDisp1);

p462509_1_3.extax.eax_c := angularDisp1;                ! ... and 13 more targets
p462509_1_4.extax.eax_c := angularDisp1;

MoveJ Offs(p462509_1_2, dTrans.x,0,0), v1000, z10, tWeldGun\WObj:=wobj_Stn1_NoCoord;

The _NoCoord work object is what makes this work, and it is easy to miss. wobj_Database.sys declares each station frame twice:

wobj_Database.sys
Work objectufprogufmecBehaviour
wobj_Stn1 / wobj_Stn2FALSESTN1 / STN2Coordinated. The frame rides the turntable; the TCP follows the part as it turns.
wobj_Stn1_NoCoord / wobj_Stn2_NoCoordTRUESTN1 / STN2Not coordinated, same geometry. The taught point stays fixed in the world; the extax in the robtarget still commands the table.

So the correction is: the feature moved, therefore rotate the table to bring the feature back to where the program was taught. With the coordinated frame that would cancel out — the path would follow the part and the offset would do nothing. With _NoCoord the taught world position holds still and the table does the work. The choice of frame is load-bearing, not cosmetic.

Step 3 — modelling the part's twist

A long tube does not just sit rotated, it sits twisted. So the measured error is scaled down for weld groups nearer the fixed end:

! six weld groups, six fractions of the measured angular error
scaledAngularDisp1 := ((angularDisp1 - initialHeadstockRot) * (41/44)) + initialHeadstockRot;   ! Weld_7
scaledAngularDisp1 := ((angularDisp1 - initialHeadstockRot) * (36/44)) + initialHeadstockRot;   ! Weld_3
scaledAngularDisp1 := ((angularDisp1 - initialHeadstockRot) * (28/44)) + initialHeadstockRot;   ! Weld_6
scaledAngularDisp1 := ((angularDisp1 - initialHeadstockRot) * (20/44)) + initialHeadstockRot;   ! Weld_3
scaledAngularDisp1 := ((angularDisp1 - initialHeadstockRot) * (12/44)) + initialHeadstockRot;   ! Weld_5
scaledAngularDisp1 := ((angularDisp1 - initialHeadstockRot) * ( 4/44)) + initialHeadstockRot;   ! Weld_4

Stations at 4, 12, 20, 28, 36 and 41 of 44 — evenly spaced 8 apart, with the last one at 41. A linear interpolation of angular error along the part's length.

It is a genuinely neat piece of process engineering. It is also six hard-coded magic numbers in executable RAPID, one shared scratch variable overwritten six times, and a denominator that only makes sense for one part geometry.

Roughly ±2.5° part to part, σ ≈ 1.2°. At a 100 mm working radius that is about 4 mm of arc error at the extremes — far outside anything a fillet weld will tolerate. The search is not a nicety; the cell does not run without it.

No error handler on any search

All 13 SearchL/SearchC instructions in the project use \Stop and none of the enclosing routines has an ERROR clause. A missed touch — dirty part, bent wire, failed cut, welder not in touch mode — aborts the part with a RAPID error rather than degrading gracefully. Given the arc error handling is fully wired to the HMI (goER_ErrType, giERActionSig), search failure is the one process fault with no operator path.

Process data

Weld data is imperial, stored in metric

This is the single most important thing to know before touching a welddata or seamdata value. PROC.cfg sets:

ARC_UNITS:   -name "CDN_UNITS" -arc_length_units "mm" -arc_velocity_units "ipm" -arc_feed_units "ipm"
ARC_SYSTEM_PROP: -name "ARC1" -units "US_UNITS" -restart_on -restart_dist 10 -scrape_opt_on

The pendant shows inches per minute. RAPID stores mm/s. Every value in mDeclarations.sys is an exact whole number of ipm — which is how you can tell the data was entered on the pendant and never hand-edited:

weavedata weave1 = [1, 0, 2.032, 4.826, 3.048, …] is the same story: 0.080″ length, 0.190″ width, 0.120″ height.

Never edit weld data in a text editor

Type 8.9 instead of 8.89 and you have silently changed 21 ipm to 21.02 ipm. Worse, a "tidy" round number in the file is a sign somebody already did. Edit these through the pendant or the RobotStudio arc data editor so the unit conversion stays exact.

The naming convention carries the joint spec

Read sm3_16_ft_tube_095_overlap as: seam data, 3/16″ fillet, on tube, 0.095″ material, closing pass. The suffix vocabulary:

  • _ft fillet, _VB vee butt · _tube / _block which member · _095 material thickness
  • _tack, _tackHI, _tack_long — tacking schedules
  • _seal, _Seal, _Weave, _Stitch, _Wrap, _craterFill — pass type
  • _overlap — the tie-in pass. Always a slower travel speed than its parent: wd3_16_ft_tube 19 ipm → wd3_16_ft_tube_overlap 10 ipm. Used on the last ArcC/ArcCEnd of every circumferential weld, so the closing overlap gets extra fill.

Weld error recovery happens on the HMI, not the pendant

ARC_ERR_HNDL_IO routes the whole recovery dialogue to the PLC: goErrActiveDiag, doDiagActive, doEscapeOK, diErrAck, giERActionSig, goER_ErrType, goER_ErrNum. The operator answers "resume / skip seam / skip part" on the cell HMI and the PLC replies through giERActionSig. Anyone rebuilding the HMI has to reimplement that state machine — it is not optional decoration.

Seam names are copy-pasted and wrong

Every weld carries \SeamName:= for the weld log. In RS461117_Stn1 all of them read "RS461117_Stn2_Weld_...". In RS462509_Stn2 and RS462509_Stn2NoIO they read "rRS462509_Stn1_Weld_...". And Weld_3 is used for two different seams in the same routine. Weld traceability data is attributing station 1's welds to station 2 and vice versa.

Welder signals — from the add-in, not from EIO.cfg

Four signals used in RAPID are not in the saved EIO.cfg; they come from the Arc option and the Miller EIP add-in's own configuration: doWld1TouchOn, diWld1TouchActive, diWld1Touched, soAwManFeedFwd. So does diWld1ArcDetect, which the ArcOn cross-connection depends on. Restore SYSPAR onto a system without the Miller add-in and the program will not compile.

EIO.cfg does define the pendant-facing pair siWld1StopProc / soWld1StopProc (category Arc_1_R1) used by the Production Screen's "Stop Process" widget, plus soWld1ManWireFeed / siWld1ManWireFeed.

Internal boards and the simulation short-circuit

B_GAP_SIM is a simulated local device carrying the whole Production Manager signal set (soGap_* / siGap_*, 60+ signals). It exists so the cell logic closes on itself. The important cross-connections:

Maintenance loops

Torch, wire and TCP integrity

Three self-maintenance loops keep the process honest, and all three are worth understanding before changing anything about the torch.

Torch cleaning, on a part counter

Utility.ServiceFlag is bound to the EE_SERVICE engine event and counts parts:

IF nTCFreqSet > 0 THEN
  Incr nTCCount;
  IF nTCCount >= nTCFreqSet TorchClean;
ENDIF
IF nSPFreqSet > 0 THEN
  Incr nSPCount;
  IF nSPCount >= nSPFreqSet ServicePos;
ENDIF

Both intervals are set from the pendant (TCFreq, SPFreq menus); 0 disables. TorchClean then goes to a pounce point, resets the cleaner, waits di2_TC_READY, descends, pulses do1_TC_START, sprays anti-spatter, trims the wire and returns to jposSafe.

The counters never reset

nTCCount and nSPCount are incremented and compared but never zeroed in any readable module. Once the threshold is passed, the condition stays true and the service runs every part. Either the reset is inside encrypted GAP_USER.sys, or the intervals are being left at 0 in production and cleaning is triggered manually from the HMI (command 101).

Separately: TorchClean waits on di2_TC_READY both before and immediately after the start pulse. If the cleaner does not drop "ready" fast enough the second wait passes instantly and the robot can lift before the ream finishes — masked by a following WaitTime\InPos, 3. TorchServices.RunReamer handles this correctly (it waits for ready to go false first) but the call to it is commented out. nCleanTime is prompted for and stored, then never used.

Wire trim

WireCutter opens the cutter, approaches the trim station in two steps, pulses soAwManFeedFwd for nWireFeedTime, closes the cutter, waits nWTrimTime, opens again. Straightforward, and the reason the touch searches are repeatable at all.

BullsEye

Version 10.2.5, beam sensor on sen1, scanning with tWeldGun and a 15 mm TCP extension. Three entry points are exposed as PLC menu commands: BERefPnt (105), BEToolCheck (106, BECheckTcp \XYZOnly \SingleScan), BEToolUpdate (107, BEUpdateTcp \XYZOnly). BEToolUpdate has a proper error handler — on ERRNO 111528 it falls back to a full unprompted setup.

A geometry check routine already exists

Testing.positionTest drives the torch to three reference points — cleaning station, station 2, station 1 — with the wire brake engaged, in a fixed order. That is a ready-made after-crash / weekly verification routine, and it is the fastest way to confirm the cell geometry has not shifted. Worth knowing it is there before writing a new one.

World zones

Four stationary spherical zones are armed by POWER_ON event routines and report robot location to the PLC: BullsEye r=200 mm, reamer r=250 mm, service position r=200 mm, wire service position r=200 mm. They are defined with WZDOSet \Stat, so they survive until the next restart and cannot be freed by the program.

Safety

Safety configuration

SafeMove Pro with a PROFIsafe F-Device. All three stop functions — General, Automatic and Emergency — are Category 1 and all three are commanded from the safety PLC over PROFIsafe. Manual mode is capped at 0.25 m/s. RUNCHN_BOOL selects soft AS, GS and SS; soft ES is not selected.

SafeMove zones — seal 2E540591, created 2025-03-05
#ZoneTop / bottomPrioritySupervision
1SafetyPerimeter+2.4 / −0.7 mBASEKeep-in, permanent, robot included. Violation → Cat 1 stop. Tool speed limited to 0.25 m/s while inside
2ProductionZone+2.3 / −0.7 mNORMALTool speed up to 4 m/s. NORMAL priority overrides the BASE limit of zone 1
3TipChange+1.5 / +0.3 mNORMALKeep-out, armed by sciConfiguration1Active from the PLC. Violation → Cat 1 stop + scoConfiguration1Violation
Read the two speed zones together

Because zone 2 sits inside zone 1 and carries NORMAL priority, the effective rule is: 250 mm/s everywhere inside the fence, except inside the ProductionZone envelope where 4 m/s is allowed. The torch-service and tip-change end of the cell is therefore permanently speed-limited. A cycle-time complaint about slow travel to the reamer is a safety-zone question, not a program question.

The torch is modelled for supervision as three capsules — TorchBody (r 40 mm), TorchNozzle (r 25 mm), TorchBracket (r 50 mm) — plus two speed supervision points, with an elbow offset of [-0.24, 0, 0.32] m and the upper arm as a capsule plus a lozenge.

Verify the safety tool against tWeldGun

SafeMove's Tool id="1" name="tWeldGun" declares TCP = [13.7, 18.5, 439.9] mm with orientation [0.8037, -0.1875, 0.3387, 0.4518]. RAPID's tWeldGun is [46.0, -18.5, 414.9] mm with [0.9016, 0.0289, 0.4313, -0.0157]. The two do not agree — about 25 mm in Z and a different orientation. Since SafeMove supervises against its own model, a mismatch shifts the real supervised point away from the real TCP. Confirm on the plant whether the safety tool was deliberately set conservative or has simply drifted since the last BullsEye setup.

Findings

Risk ledger

Ordered by what would bite hardest, not by where it appears in the code.

Blocks work
The virtual controller here is RobotWare 6.15.8029; the plant is 6.16.0025
The backup was taken from a 6.16.0025 system (BACKINFO/version.xml, program.id). The VC RobotStudio built on this machine (Virtual Controllers/…/system.xml) is 6.15.8029, because 6.16.0025 media is not installed locally. Install RobotWare 6.16.0025 and Positioner 6.16.0025 before trusting anything you simulate.
Safety
The VC has no SafeMove configuration
The active safety config in the VC (INTERNAL/SC_DISK/sc_cfg.xml) is the 2015 RW 6.09 default — seal 88036456, zero zones — and sc_eio.cfg is empty. The real configuration (seal 2E540591) exists only as a file in HOME/Safe Move/ and inside the May-2025 backup under User Files. Nothing you simulate will trip on the perimeter or the 250 mm/s base limit; the real robot will.
Incomplete
35 of the declared parts have no code in this backup
mDeclarations.sys declares 24 production parts (IDs 1001–1036, 1500). Only RS461117_Stn1/Stn2 and RS462509_Stn1/Stn2 have routines. Production Manager will list the rest and fail on selection. Their targets and paths exist only as station data in Monarch_1.2R2.rsstnx — and the station also holds an older generation of modules (m461117, m461541, m461547, … m722067) alongside the current mRS… set. Get a full plant backup, or Synchronize-to-RAPID from the station and be deliberate about which generation you take.
Process
No error handling on 13 search instructions
Every SearchL/SearchC uses \Stop with no ERROR clause anywhere up the call chain. A missed touch aborts the part. This is the one process fault with no operator recovery path, in a cell where everything else routes to the HMI.
Data integrity
Seam names misattribute welds between stations
RS461117_Stn1 logs every weld as "RS461117_Stn2_Weld_n"; RS462509_Stn2 and its _NoIO twin log as "rRS462509_Stn1_Weld_n"; Weld_3 is reused for two seams. If anyone is consuming the weld log for traceability, it is wrong.
Motion
Station 1's payload data is a placeholder
Station 1's loaddata is [250, [0.001, 0.001, 0.001], [1,0,0,0], 30, 30, 60] — a mass with a COG at the origin and round-number inertias. Station 2's is [340, [0.1, 0.4, 901.4], [1,0,0,0], 476.9, 25.4, 2.6], which is clearly measured. The two arms also differ in ARM_TYPE mass: ARM1 892 kg vs ARM2 806 kg. Positioner path accuracy, servo tuning and collision-detection thresholds all read this data.
Operations
ModPos tuning is enabled in AUTO, and the PP warnings are off
SYS.cfg: HOTEDIT_MODPOS -tuning_in_auto lets positions be tuned in automatic mode. WARN_AT_START sets cursor_pp_diff_warning 0 and show_pp_to_cursor_button 0, so the "program pointer differs from cursor" warning is suppressed and PP-to-cursor is hidden. Deliberate operator-convenience choices, but they mean taught positions can change in production with no record.
Restore hazard
ApplSys still holds the untouched ABB templates
SYS.cfg → CAB_TASK_MODULES auto-loads HOME:/ApplSys/PartR1S1.mod, PartR1S2.mod and gapMain.mod. Those files are the original templates: ProgStn1 is a comment block ending in Stop; and pdProgStn1 has part ID 0, against 9.7 KB of real code and ID 111 in the saved program. Establish which copy is authoritative before any restore or Reset RAPID.
Cycle
ArmsToZero_DPos ends with Stop; and is bound to EE_CLOSE_JIG
A bare Stop; in an execution-engine event routine halts the cycle. ServicePos and ServiceWirePos also end in Stop;, which is intentional there (the operator works on the torch, then presses start). In ArmsToZero_DPos it looks accidental.
Uncontrolled motion
m2ndLoadPos moves the machine from inside a TRAP
ActUnit → MoveJ → DeactUnit inside STN1LoadPos2TRAP, triggered by a PLC signal that can arrive at any point in the cycle. Whatever prevents this firing with the torch inside the part lives on the PLC side.
Test code
Mismatched activation in the test routines
Testing.laserTest does ActUnit STN1 three times against two DeactUnit STN2 — net +2 on STN1, −2 on STN2. Testing.positionTest activates STN2 then STN1 without deactivating. gapMain.MockRoutine, mRSTestFixture and mRSTestFixture2 activate STN1/STN2 and never release. Harmless because every production routine opens with DeactUnit, but these will error if run in the wrong order.
Dead code
Orphaned and shadowed declarations
initialHeadstockRot2, angularDisp2, scaledAngularDisp2, nTestCount, tool1, tWeldGunNew — declared once, used nowhere. mLogging.CheckAndLog2 logs angularDisp1 instead of angularDisp2, and neither CheckAndLog routine is called from any readable module even though the CSVs hold 285 and 292 samples. Utility.declarations() contains a bare <SMT> placeholder. mRSTestFixture.mod declares a LOCAL PERS wobj_Stn1 that shadows the global one with a zero user frame. SyncPos.mod and SafeTest.mod reference obBETemp, which is not declared in any module in this backup.
Framework
GoSafe park and service positions are not defined
ROB1_1_HomeData has the safe position filled in and flagged TRUE; the park and service entries are 9E+09 with FALSE. The SetParkPos1 / CheckParkPos1 / SetServicePos1 menus exist but have nothing to act on. Note this is separate from Utility.ServicePos, which is the cell's own torch-service move and does work.
Fragile
Hard-coded absolute path in mLogging
/hd0a/4600-803651/HOME/log/VariableLog1.csv embeds the system name. Rename the system and the logging silently stops (the Open will raise, with no handler). Use HOME:/log/… instead.
Pendant
Production Screen widget DLLs are missing
ProductionSetup.xml declares TpsViewMillerDataEditor.dll and TpsViewMillerWeldInfo.dll, neither of which is in HOME/ProdScr/tps/ — they come from the Miller add-in at runtime. ProdScr.log in the May-2025 backup shows FileNotFoundException for the arc-status and process-stop widgets too; those two DLLs have since been added. Expect widget load errors on a VC without the full add-in media.
Opacity
Four modules are encrypted
GAP_USER.sys, GAP_PARTADV.sys, GAP_PARTADV_SHRD.sys, ProdScr.sys. Anything you cannot account for — the service-counter reset, the CheckAndLog callers, the ActStn/IndexToStn wrappers' menu bindings — is probably in there. Plan around the interface, not the implementation.
