Monarc RAPID Primer

Every RAPID construct that actually appears in this cell's programs, defined from ABB's manuals and then shown doing its job in the customer's own code. Heaviest on external axes, because that is where this cell's difficulty lives.

How definitions here were checked

Instruction and data-type definitions are taken from ABB's Technical reference manual — RAPID Instructions, Functions and Data types (3HAC16581-1 rev P). Record layouts (seamdata, welddata, partdata…) are read from the descriptor XMLs shipped with this system's own Arc option, so the field order matches the controller rather than a generic manual. The logical-axis map comes from the installed Positioner media pool. Full list at the end.

Foundations

Anatomy of one line

If you can read this one line, you can read 80% of the cell.

Two conventions to internalise immediately:

  • \Something is optional. \WObj:= takes a value; \NoEOffs is a bare switch — its presence is the argument.
  • fine versus z10 is the single most consequential choice on a move line. fine is a stop point: the robot actually arrives and stands still, and the program waits. z10 is a fly-by point: the robot corners through within 10 mm and the program runs ahead. Several real problems in this cell trace back to a fly-by where a stop point was required.

Foundations

Declarations and storage classes

A MODULE is a file. Inside it, data declarations first, then routines.

Storage classes, and why the choice matters here
KeywordLifetimeIn this cell
VARReset on program start / PP to mainVAR pos dTrans; — the search correction. Deliberately volatile: a fresh part re-measures it.
CONSTNever changesCONST jointtarget jposSafe:=... — the home position. Cannot be modified from the pendant, which is the point.
PERSSurvives restart and power lossAll weld data, all part data. When a persistent's value changes, the controller rewrites the declaration's initial value, so what you see in the module is the live value.
TASK PERSPersistent, but private to one taskTASK PERS tooldata tWeldGun. A plain PERS of the same name is shared across tasks; TASK PERS is not.

Trap — PERS means the file lies to you

Because PERS declarations are rewritten with their current value, the numbers you read in mDeclarations.sys are whatever the last operator left there — not what a programmer typed. Never treat a PERS initial value in a backup as intent. CONST values, by contrast, are intent.

Module attributes

MODULE Utility(SYSMODULE) — a system module: it is not erased by "delete program", and it is not saved as part of the program. (READONLY) blocks edits from the pendant (used on Irbp1Data.sys, IrbpSetup.sys). (NOSTEPIN) makes step-by-step execution treat routines as a single step.

Routines

PROC does something and returns nothing. FUNC num Name() returns a value. TRAP is an interrupt handler — you never call it, the system does. UNDO and ERROR are optional blocks inside a routine; ERROR is where recovery goes, and its absence is the biggest single weakness in this cell's part programs.

Foundations

Motion instructions and their data

MoveJ ToPoint, Speed, Zone, Tool [\WObj]

Joint move. All axes interpolate together; the TCP takes whatever curved path results. Fastest way between two points, but the path is not predictable — never weld with it.

MoveL ToPoint, Speed, Zone, Tool [\WObj]

Linear move. The TCP travels in a straight line. Used for approach/retract and for any motion where clearance matters.

MoveAbsJ ToJointPos [\NoEOffs], Speed, Zone, Tool

Move to absolute joint angles rather than a Cartesian pose. The destination is a jointtarget, so there is no inverse-kinematics ambiguity — this is why "go home" is always a MoveAbsJ.

\NoEOffs is precisely: "If the argument \NoEOffs is set then the movement with MoveAbsJ is not affected by active offsets for external axes." It suppresses any active EOffsSet displacement — it does not mean "ignore the external axes".

Offs(Point, XOffset, YOffset, ZOffset) → robtarget

A function, not an instruction: returns a shifted copy of a position. The shift is applied in the object coordinate system of the work object, not in world.

! mRS461117.mod — the whole taught path shifted by the measured error
ArcLStart Offs(p461117_1_140, dTrans.x, dTrans.y, dTrans.z), v300,
          sm3_16_ft_block, wd3_16_ft_block_095, fine, tWeldGun\WObj:=wobj_Stn1;

This is the "shift every point by hand" style of correction. RAPID also has PDispSet/PDispOn, which apply a displacement to all subsequent moves until turned off — fewer edits, less risk of missing a point. This cell does not use them.

External axes

extax and logical axes

This is the concept that makes the Monarc programs readable. Get it and the rest follows.

Both robtarget and jointtarget end with an extax field of type extjoint, which has exactly six slots:

RECORD extjoint
    eax_a  eax_b  eax_c  eax_d  eax_e  eax_f
ENDRECORD

The manual is precise about what these are:

"Additional axes eax_a… are logical axes. How the logical axis number and the physical axis number are related to each other is defined in the system parameters. The value 9E9 is defined for axes which are not connected."

So eax_a…eax_f are slots 7–12 of the drive module, and which physical motor sits in a slot is a configuration question, not a programming one. In this cell the configuration reuses slots:

Monarc logical-axis map, from the installed Positioner config
SlotLogical axisWhen STN1 is activeWhen STN2 is activeWhen INTERCH is active
eax_b8ARM1 (station 1 tilt)ARM2 (station 2 tilt)INTERCH_PLATE1
eax_c9PLATE1 (turntable 1)PLATE2 (turntable 2)INTERCH_PLATE2
eax_d10——INTERCH (the 180° index axis)
eax_a, eax_e, eax_f7, 11, 12not connected (9E9)not connectednot connected
The single most important gotcha in this cell

eax_b and eax_c mean different physical motors depending on which mechanical unit is active. A robtarget copied from a station-1 routine into a station-2 routine will happily drive station 2's tilt and turntable to station 1's angles. Nothing warns you. This is why the two PartR1S1/PartR1S2 templates look almost identical yet must never be interchanged.

Now this line from mRS462509.mod reads cleanly:

! read the turntable angle at the moment the wire touched the part
angularDisp1 := pSearchPt_1W.extax.eax_c;

! then write that angle into every taught weld point
p462509_1_10.extax.eax_c := angularDisp1;

With STN1 active, eax_c is turntable 1. The code is saying: "the feature was found at table angle X, so command the table to X at every weld point."

The 9E9 rule, and why it bites

9E9 means "this slot is not in play". The manual spells out the consequence:

"If the position is not defined in the position data (value 9E9) the value will be ignored, if the axis is connected and not activated. But if the axis is activated it will result in error."

So a robtarget with [9E+09, 9E+09, ...] in extax is only safe while no positioner unit is active. Their code respects this — jposSafe and all the torch-service positions carry all-9E9 extax and are always reached after a DeactUnit:

DeactUnit STN1;
MoveAbsJ jposSafe\NoEOffs, v1000, z50, tWeldGun;   ! jposSafe extax = all 9E9 — legal only because STN1 is off
Worth checking on the plant

TorchClean, ServicePos and WireCutter all move to all-9E9 positions, and TorchClean can be triggered by the EE_SERVICE event or by PLC menu command 101. If either fires while a station is still active, that is the error the manual describes. The part routines always deactivate first, so the normal path is clean — it is the event-driven path that is worth verifying.

External axes

ActUnit / DeactUnit and friends

ActUnit MechUnit; DeactUnit MechUnit;

Bring a mechanical unit under the controller's control, or release it. The manual's own words on why they exist:

"It can be used to determine which unit is to be active when, for example, common drive units are used."
"If several mechanical units share a common drive unit, activation of one of these mechanical units will also connect that unit to the common drive unit."

That is exactly this cell: five positioner motors, three drive units, contactors K1–K5 doing the switching. An inactive unit "will neither be controlled nor monitored" — brakes on, position still measured, but not commanded.

Documented limitations — all three apply here

1. "If this instruction is preceded by a move instruction, that move instruction must be programmed with a stop point (zonedata fine), not a fly-by point, otherwise restart after power failure will not be possible."

2. Neither can run in an event routine for PowerOn, Stop, QStop, Restart, Reset or Step.

3. DeactUnit "cannot be used when one of the mechanical units is in independent mode" — relevant because both turntables are configured independent_joint_on.

Their code breaks limitation 1 
MoveJ p461117_2_240, v1000, z100, tWeldGun\WObj:=wobj_Stn2;
DeactUnit STN2;

Every part routine ends this way — a 100 mm fly-by immediately before DeactUnit. Per the manual this costs you restart-after-power-failure at that point in the cycle. It will not throw an error and it will not be noticed until a power dip happens mid-cycle. The fix is one character-group: z100 → fine.

MechUnitLoad MechUnit, AxisNo, Load;

Tell the controller what the positioner is carrying, so its dynamic model is right. Axis numbering starts at 1, and the manual says it "should always be executed after execution of the instruction ActUnit".

! Irbp1Prc.ActStn1 — the framework does this for you
IF (NOT IsMechUnitActive(STN1)) ActUnit STN1;
MechUnitLoad STN1, 2, ldLoadStn1;    ! axis 2 of STN1 = PLATE1, the turntable

The manual warns that wrong load data causes "impaired path accuracy including a risk of overshooting" and "risk of overloading the mechanical structure". Station 1's load in this cell is [250, [0.001,0.001,0.001], ...] — a mass with its centre of gravity at the origin, which is a placeholder, not a measurement.

IsMechUnitActive(MechUnit) → bool

Ask before you act. Lets the framework be idempotent: activate only if not already active.

MoveExtJ [\Conc] ToJointPos [\ID] [\UseEOffs] Speed [\T] Zone [\Inpos]

Move external axes when there is no robot in the task. The manual: "This instruction can only be used with an actual program task defined as a Motion Task and if the task controls one or several mechanical units without TCP."

Note there is no Tool and no \WObj — there is no TCP to speak of.

TaskRunRob() → bool

"Check if the program task controls some robot (mechanical unit with TCP)." TRUE in T_ROB1 on this system.

Those last two explain a pattern that appears seven times in this cell and looks baffling at first:

ActStn1;
jtCurrent := CJointT();               ! read where all axes are right now
jtCurrent.extax.eax_b := -20;         ! change only the tilt
jtCurrent.extax.eax_c := 90;          ! and the turntable
IF (TaskRunRob()) THEN
    MoveAbsJ jtCurrent, vStation1, fine, tool0;      ! this task has a robot → normal move
ELSE
    %"MoveExtJ"% jtCurrent, vStation1, fine;         ! positioner-only task → external-axis move
ENDIF
DeactStn1;

From PartR1S1.ProgStn1. This is ABB's "Same task for IRB/IRBP" idiom: one module that works whether the positioner lives in the robot's task or in its own. On the Monarc there is only T_ROB1, so the ELSE branch never runs.

Read the pattern as a three-step recipe, because you will write it yourself:

  1. CJointT() — snapshot every axis, so the robot joints stay exactly where they are.
  2. Overwrite only the extax slots you want to move.
  3. MoveAbsJ the whole snapshot. The robot holds still; the positioner moves.

That is how you say "rotate the table, don't touch the arm" in a language that has no such instruction.

External axes

Coordinated work objects — the trick this cell turns on

A wobjdata is [robhold, ufprog, ufmec, uframe, oframe]. Two of those fields decide whether the robot follows the positioner:

wobjdata, from the manual
FieldValueMeaning
robholdFALSEThe robot holds the tool, not the work object.
ufprogTRUE"Fixed user coordinate system." The stored uframe is used literally.
ufprogFALSE"Movable user coordinate system, i.e. coordinated external axes are used." And: "For movable user frame, the user frame is continuously defined by the system."
ufmec"STN1""The mechanical unit with which the robot movements are coordinated. Only specified in the case of movable user coordinate systems."

The Monarc declares each station frame twice, differing in one boolean:

! wobj_Database.sys
PERS wobjdata wobj_Stn1        :=[FALSE,FALSE,"STN1",[[1278.3,640.454,421.695],[...]],[[0.16,92.37,158.88],[...]]];
PERS wobjdata wobj_Stn1_NoCoord:=[FALSE,TRUE ,"STN1",[[1278.3,640.454,421.695],[...]],[[0.16,92.37,158.88],[...]]];

Same geometry, opposite behaviour:

  • wobj_Stn1 (coordinated) — the frame rides the turntable. Rotate the table mid-weld and the TCP tracks the part. This is what you want for welding a seam while the part turns.
  • wobj_Stn1_NoCoord (not coordinated) — the frame is nailed to the world. The extax in the robtarget still commands the table, but the taught XYZ does not move with it.
Why the correction needs the non-coordinated twin

The mRS462509 correction rotates the table so the found feature lands where the program was taught. With the coordinated frame that would cancel itself out: rotate the table, the frame rotates with it, the TCP follows, net zero. With _NoCoord the taught point stays put in world and the table does the correcting. Swapping the two work objects would silently disable the entire part-location scheme while the program still ran and still welded — just in the wrong place.

Two more work-object families exist in the cell and are not interchangeable with these: wobjStation1/wobjStation2 (from the ABB template, coordinated but with a zero object frame) and plain wobj0 (world). Check which family a routine uses before copying points out of it.

External axes

The interchange, line by line

Everything so far, working together. This is Irbp1Prc.IndexToStn1 — ABB's code, not the customer's, and the best worked example in the system.

PROC IndexToStn1()
  IF (NOT bInterchCalib1) CalibIntch1;              ! 1. refuse to index if the axis isn't calibrated
  Reset soLS_1_INPOS;                               ! 2. clear the simulated "station in position" flags
  Reset soLS_2_INPOS;
  bActive := IsMechUnitActive(INTERCH);
  IF (NOT bActive) ActInterch1;                     ! 3. take the index unit (all 3 axes) + set payloads
  jtCurrent := CJointT();                          ! 4. snapshot every axis

  GetNextPartAdv 1, padvTmp1 \statusCode:=retCode1;   ! 5. what's queued for each side?
  GetNextPartAdv 2, padvTmp2 \statusCode:=retCode2;

  jtCurrent.extax.eax_b := padvTmp1.procAngle.eax_c;   ! 6. side 1 → its PROCESS angle
  jtCurrent.extax.eax_c := padvTmp2.loadAngle.eax_c;   !    side 2 → its LOAD angle
  jtCurrent.extax.eax_d := nInterchStn1;               ! 7. and the index axis to -0.249999°

  IF (TaskRunRob()) THEN
    MoveAbsJ jtCurrent, sdInterch1, fine, tool0;      ! 8. ONE move: swing + both tables together
  ELSE
    %"MoveExtJ"% jtCurrent, sdInterch1, fine;
  ENDIF

  IF (NOT RobOS()) Set soLS_1_INPOS;               ! 9. fake the limit switch — virtual controller only
  WaitTime nTorqueTime;                             ! 10. 0.4 s for torque to settle
  DeactInterch1;                                   ! 11. release the drives
  WaitUntil IsMechUnitActive(INTERCH) = FALSE;      !     and don't continue until it's really off
ENDPROC

Things worth pulling out of that:

  • Step 8 is one instruction. The 180° swing and both turntable rotations happen in a single coordinated MoveAbsJ, so each side arrives pre-oriented. No separate positioning move afterwards — that is where the cycle time is won.
  • Step 8 ends in fine, because step 11 is a DeactUnit. ABB's own code obeys the limitation the customer's part routines break.
  • Step 6 mixes slots deliberately. The part's angle is authored in the partadv record's eax_c field, then written into the interchange unit's eax_b or eax_c. Same physical motor, different slot, because a different mechanical unit is active. Exactly the trap described earlier — handled correctly here.
  • RobOS() in step 9 returns TRUE on a real controller, FALSE in a virtual one. The line means "in simulation, pretend the station-in-position switch closed". Useful to know when a behaviour reproduces in RobotStudio but not on the floor, or vice versa.

Process

SearchL and SearchC

SearchL [\Stop]|[\PStop]|[\SStop]|[\Sup] Signal [\Flanks]|[\PosFlank]|... SearchPoint ToPoint [\ID] Speed [\V]|[\T] Tool [\WObj] [\Corr] [\TLoad]

Move toward ToPoint while watching a digital input. The instant it changes, record where the robot was into SearchPoint. SearchC is the same thing along a circular path (it takes a via-point as well).

Critically, SearchPoint is a full robtarget — "the position of the TCP and external axes when the search signal has been triggered". That external-axis part is what this cell actually uses.

The stop switches — pick one deliberately
SwitchBehaviourStop distance at 50 mm/s
\StopHard stop, TCP leaves the path. Fastest. Only allowed below 100 mm/s — above that "some axes can move in unpredictable directions".1–3 mm
\PStopDecelerates while keeping the TCP on the path.15–25 mm
\SStopSoft stop, TCP near the path. Faster than \PStop; above 100 mm/s it slides slightly off tangentially.4–8 mm
\SupDon't stop at all — "flying search". Keeps watching the whole move and errors if it gets more than one hit.n/a
(none)Flying search, but no error on multiple hits — the first hit is returned.n/a

In every case the robot overshoots and is not moved back to the found position — but SearchPoint holds the true trigger position, so the recorded value is still good. Documented repeatability is 0.1–0.3 mm.

Their usage, checked against the manual 
SetDO doWld1TouchOn, 1;                    ! energise the wire as a probe (SmarTac via the Miller)
WaitDI diWld1TouchActive, 1;               ! wait for the welder to confirm sensing is live
MoveJ pSearch_1W_n26, v100, z100, tWeldGun\WObj:=wobj_Stn1;
WaitTime 3;
SearchC\Stop, diWld1Touched, pSearchPt_1W, pSearch_1W_n22, pSearch_1W_n18, v5, tWeldGun\WObj:=wobj_Stn1;
SetDO doWld1TouchOn, 0;

Good: v5 is 5 mm/s, far below the 100 mm/s ceiling for \Stop. That part is right.

Not good: the move immediately before the search uses z100. The manual's Limitations section is explicit — "the start of the search, i.e. when the I/O signal is ready to react, is not… the programmed destination point of the previous positioning instruction but a point along the real robot path" — and illustrates matching on the wrong side of the object, or missing it entirely. It should be fine. Note that Testing.laserTest does use fine here, so the correct form was known.

Also: WaitTime 3 waits three seconds of program time, which after a fly-by point is not the same as three seconds of the robot standing still. WaitTime\InPos, 3 is the form that guarantees the robot has arrived — and it is used elsewhere in TorchServices.sys, so again the right idiom is in the codebase.

Three errors, no handlers

The manual lists exactly when a search errors:

  • ERR_WHLSEARCH — no signal detected. Movement continues to the destination; no position returned.
  • ERR_WHLSEARCH — more than one detection, but only if \Sup was used.
  • ERR_SIGSUPSEARCH — the signal was already high when the search started, or communication with it was lost. This one applies specifically when \Flanks is omitted, which is the case in all 13 searches here. A wire already touching the part, or slag bridging the gap, lands you here.

None of the enclosing routines has an ERROR block, so any of these aborts the part. The standard pattern is short:

SearchC\Stop, diWld1Touched, pSearchPt_1W, ..., v5, tWeldGun\WObj:=wobj_Stn1;
...
ERROR
    IF ERRNO = ERR_WHLSEARCH THEN
        TPWrite "Search found nothing — retrying";
        RETRY;                  ! re-run the instruction that failed
    ELSEIF ERRNO = ERR_SIGSUPSEARCH THEN
        WireCutter;             ! wire was already touching — re-trim and retry
        RETRY;
    ENDIF

RETRY repeats the failed instruction; TRYNEXT skips past it and continues.

Process

I/O instructions

SetDO Signal, Value;

Set a digital output to 0 or 1. Used 74 times in this cell — it is how the robot talks to the PLC. Set/Reset are the shorthand forms for 1 and 0.

PulseDO [\High] [\PLength:=seconds] Signal;

One pulse, default 0.2 s, range 0.001–2000 s. Execution continues immediately — "the next instruction after PulseDO is executed directly after the pulse starts". \High forces a rising pulse regardless of the signal's current state.

PulseDO\High\PLength:=1, do1_TC_START;   ! 1 s start pulse to the Binzel reamer
WaitDI Signal, Value [\MaxTime] [\TimeFlag] [\Visualize ...];

Block until an input reaches a value. Without \MaxTime it waits forever, which is usually what you want for a PLC handshake and never what you want for a device that can fail.

\Visualize puts an explanatory dialogue on the pendant while waiting — a genuinely nice touch in TorchServices.sys:

WaitDI di2_TC_READY, 1\Visualize
    \Header:="Waiting for R1 Torch Clean Ready"
    \MsgArray:=["Movement will not continue until","Stroke is down and","clamp is open."]
    \Icon:=iconError;

Compare with the bare WaitDI diReadyToResumeProg, 1; in the part routines — same indefinite wait, but the operator gets no idea what the robot is waiting for.

GInput(Signal) → num

Read a group input as a number. Group signals bundle consecutive bits into one integer.

nTableAng := GInput(giTableAngle);        ! PLC sends the requested table angle
IF diTableAngNeg = 1 nTableAng := nTableAng * (-1);  ! separate bit carries the sign

The sign-bit workaround is there because group inputs are unsigned.

2.032 / 4.826 / 3.048 mm are 0.080″ / 0.190″ / 0.120″. Which brings us to the thing you must know before touching any of these numbers:

Every weld number in this cell was typed in inches per minute

PROC.cfg sets arc_velocity_units "ipm" and arc_feed_units "ipm". The pendant shows ipm; RAPID stores mm/s. Every stored value converts to an exact whole ipm — 169.333 → 400, 158.75 → 375, 8.04333 → 19, 8.89 → 21 — which is how you can tell nobody has hand-edited them.

Type 8.9 where 8.89 was and you have silently moved 21 ipm to 21.02 ipm. Edit weld data through the pendant or the RobotStudio arc data editor, never in a text editor. And treat a suspiciously round number in the file as evidence that someone already did.

Reading their naming convention

sm3_16_ft_tube_095_overlap = seam data, 3/16″ fillet, on the tube member, 0.095″ material, closing pass. _VB is vee-butt; _tack/_tackHI are tacking; _overlap is the tie-in pass at the end of a circumferential weld and always carries a slower travel speed than its parent (19 ipm → 10 ipm) so the closure gets extra fill.

Framework

World zones

A world zone is standing supervision: define a volume, then have the controller drive an output whenever the robot is inside it. It works during jogging too, not just program execution — that is the point of them.

Always two steps. First define a shape into a shapedata variable, then activate it:

VAR wzstationary WZ_RE;
VAR shapedata RE_volume;

WZSphDef \Inside, RE_volume, pAtTrchCln.trans, 250;      ! a 250 mm sphere at the reamer
WZDOSet \Stat, WZ_RE \Inside, RE_volume, doR1AtReamer, 1;  ! inside it → tell the PLC
ConstructMeaning
\Stat + wzstationaryStationary zone: lives until the next controller restart and cannot be freed by the program. The four service zones here are set up by POWER_ON event routines.
\Temp + wztemporaryTemporary zone: can be released with WZFree. Used by m2ndLoadPos, which redefines its zone on every request.
\Inside / \Before\Inside sets the output while in the volume; \Before sets it as early as possible before reaching it — for warning a PLC in advance.
WZHomeJointDefA zone in joint space rather than Cartesian — "to be used as a HOME or SERVICE position". Takes a centre jointtarget and a per-axis tolerance jointtarget.
 
! m2ndLoadPos.sys — is the table within 2° tilt / 3° rotation of the requested load angle?
PERS jointtarget jdelta_pos := [[2,2,2,2,2,2],[9E+09,2,3,9E+09,9E+09,9E+09]];
WZHomeJointDef \Inside, joint_space_STN1, jSTN1_2ndLoadPos, jdelta_pos;
WZDOSet \Temp, STN1_worldzone \Inside, joint_space_STN1, soAtSTN1_2ndPos, 1;

The 9E9 entries mean "don't care about this axis" — the same convention as everywhere else.

Framework

Interrupts and TRAPs

Three pieces, always in this order:

VAR intnum iSTN1LoadPos2;                            ! 1. a handle

PROC rSTN1LoadPos2()
    IDelete iSTN1LoadPos2;                          ! 2. clear any previous subscription
    CONNECT iSTN1LoadPos2 WITH STN1LoadPos2TRAP;      !    bind the handle to a TRAP
    ISignalDI siSTN1LoadPos2, 1, iSTN1LoadPos2;      !    fire it when this input goes to 1
ENDPROC

TRAP STN1LoadPos2TRAP                                ! 3. the handler — never called by you
    pCurrent := CRobT(\Tool:=tWeldgun);
    ...
ENDTRAP

The IDelete-then-CONNECT pattern is deliberate: CONNECT on an already-connected handle is an error, so you clear first. Add \Single to ISignalDI for a one-shot instead of a recurring interrupt.

Motion inside a TRAP

STN1LoadPos2TRAP does ActUnit → MoveJ → DeactUnit. A TRAP interrupts whatever the program was doing, at any moment, on a PLC signal. Moving machinery from inside one is legal but it means the positioner can start rotating at a time no-one chose. Whatever prevents that firing with the torch inside the part is on the PLC side and is not visible from RAPID.

Production Manager data types

These are not core RAPID — they come with option 812-1 and are what turn this from a program into a cell. Component names below are from the descriptors installed on this system.

ExecEngine;

The whole of main(). A loop that watches the Production Manager I/O interface and dispatches whichever part the PLC or the pendant selects. You never write the cycle logic yourself; you write parts and hang them off events.

Three extjoint angle sets plus a loaddata. Reading this one: weld with the turntable at 0°, rotate to 90° for loading, no special service angle, 250 kg payload. Change a part's load angle from the pendant and the positioner behaves differently with no RAPID edit.

ee_event — hooking into the cycle

CONST ee_event ee_ArmsAtZero := [EE_CLOSE_JIG, "ArmsToZero_DPos", "", 1, GAP_STN_1+GAP_STN_2];
!                               when            call this            task  which stations

The engine calls your routine at defined moments. The ones used here are EE_PROC_START, EE_PRE_PROD, EE_WAIT_ORDER, EE_SERVICE and EE_CLOSE_JIG. EE_CLOSE_JIG firing before the jig closes is what levels both tilt axes before the positioner swings — collision avoidance implemented as an event subscription rather than a line of code, which is why you won't find it by reading the part routines.

Odd syntax you'll hit in these files

You seeIt means
%"MoveExtJ"%Late binding. The routine name is resolved at runtime from a string instead of at compile time. Used so a module loads even on a system where that instruction or routine doesn't exist. Procedure calls only — not functions.
<SMT>A placeholder for a statement — an unfinished line. It is not an instruction. Executing it raises an error. Utility.declarations() contains one; harmless only because nothing calls it.
MoveL *, v100, ...An inline position — the target is stored in the instruction itself rather than in a named variable. Common in pendant-taught code.
\Inpos:=inpos50A convergence criterion that replaces the zone: "arrive to within this tolerance and settle" rather than just "get within 50 mm".
Stop;Halts program execution; the operator must press start. Legitimate in ServicePos (the operator works on the torch). Almost certainly leftover debug at the end of ArmsToZero_DPos, which is bound to a cycle event.
\NoEOffsIgnore active external axis offsets. Not the same as ignoring the external axes.
9E+09"This axis is not in play." Legal only while that axis's unit is deactivated.
TASK PERS vs PERSPERS of the same name is shared across tasks; TASK PERS is private to one. On a single-task system like this one the distinction is cosmetic — until someone adds a task.

A five-minute exercise

Open mRS462509.mod at RS462509_Stn1 and read the first 25 lines. You should now be able to say, for each line, which of these it is: a PLC handshake, a wire-preparation step, a drive-allocation step, a measurement, or a correction. If a line resists classification, it is almost certainly one of the extax assignments — and that is the section to re-read.
